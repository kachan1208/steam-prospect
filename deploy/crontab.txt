#
# Install:  crontab /root/prospect/deploy/crontab.txt   &&  crontab -l | head
# Verify :  crontab -l | diff - /root/prospect/deploy/crontab.txt && echo in-sync
#
# RECONCILED AGAINST THE LIVE BOX 2026-08-29 (`crontab -l`). The previous version of this
# file was reconstructed from script comments and differed from reality in three ways that
# would each have caused harm on install:
#
#   1. It DROPPED `systemd-run --scope -p MemoryMax=1500M -p MemorySwapMax=0` from the two
#      keepers and the quiet window. Those caps are not decoration: this box has 3.9GB, the
#      socials keeper has been observed leaking to 3.2GB, and an unbounded keeper OOM-kills
#      whatever else is running. Installing without them would have removed the fix that a
#      previous outage bought. They are preserved verbatim below.
#   2. It carried an 05:00 twitch collector. There is NO twitch line on the live box — the
#      creator vertical was retired product-wide (the mart, the dashboards and the source
#      table are all gone), so the job was correctly deleted at some point and must not be
#      resurrected. Dropped.
#   3. It scheduled the light build at 13:00; the box runs it at 13:30. Live time kept.
#
# PATHS POINT INTO THE GIT CHECKOUT (/root/prospect/deploy/...). Every script resolves its
# helper as "$(dirname "$0")/lib.sh", so running from the checkout is correct — and it makes
# `git pull` the whole deploy for shell changes, which removes the /root copy that used to
# drift from the repo (the copy at /root/prospect-refresh.sh is now unused; delete it once
# you have seen one clean nightly from this file).
#
# Everything runs under cron-wrap.sh, which takes the lock nonblocking and pushes
# prospect_pipeline_step_success{step="<job>"} for the job. That is what makes a job
# MONITORED: alert_check.py's headline check is "any step_success == 0 in the last 24h", and
# before wrapping, only the nightly and the light build pushed that series at all — a repeat
# of the "22 of 26 nightlies failed silently" incident on any other job would still have been
# silent. A skipped run (lock held) pushes prospect_cron_skipped and exits 0.

SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# ── 21:00 UTC — the nightly: scrape lanes, ETL, validate, swap the mart, restart the app.
# Owns /root/.prospect-refresh.lock for its whole life (3-6h), which is what keeps the
# daytime keepers out of the ETL's way.
0 21 * * * /root/prospect/deploy/cron-wrap.sh nightly_refresh /root/prospect/deploy/prospect-refresh.sh

# ── 06:00 UTC — daytime review-coverage keeper. Deepens sampled review TEXT toward
# min(true_total, 20k) for every 50+-review game. 13h timeout ends before the 21:00 nightly;
# takes the refresh lock so it cannot overlap a still-running one. Self-draining: exits in
# seconds once coverage is full (which is why the box is often idle inside this window).
#
# THIS STEP OOM-KILLED TWICE (08-30 rc=137 after 1687s, 09-01 rc=137 after 1945s; 08-31 was a
# lock skip, not a success) AND THE CAUSE IS FIXED IN THE SCRAPER, NOT HERE. Recorded in this
# file because steam-scraper has no version control, so this is the only versioned home for it.
#
# The kernel's kill line said anon-rss 1,527,188kB after 1,720 of 5,596 games / 374,278 reviews
# — ~0.85MB per game, RISING with the run, i.e. memory scaled with games PROCESSED rather than
# with concurrency. That is a retention bug, not a working set: every bulk fetch built
#     futures = {executor.submit(fetch, appid): appid for appid in appids}
# submitting the whole queue at once, so the dict held a strong reference to every Future for
# the entire run. A completed Future keeps its _result, so review payloads already written to
# SQLite could never be collected. Fixed 2026-09-01 by releasing each Future as it lands
# (`futures.pop(future)`) at all 12 sites in scraper.py plus one in news_scraper.py. Measured
# on a 400x512KB reproduction: +207MB retained before, +0MB after.
#
# --limit stays 15000 deliberately: a smaller limit was drafted as a mitigation BEFORE the
# cause was found, and shipping it now would cap coverage permanently for no reason. The 1500M
# cgroup cap remains the safety net, and alert_check reports a recurrence.
#
# timeout 46800 -> 25200 (13h -> 7h), 2026-09-02. FIXING THE OOM IS WHAT CREATED THIS BUG.
# cron-wrap takes /root/.prospect-refresh.lock, which light_build (13:30) needs too. While this
# step OOM-died at ~30min (1687s, 1945s) it released the lock long before 13:30 and nobody
# noticed the overlap. Now that it survives — 2026-09-01 ran 10618s and 2026-09-02 ran 9169s,
# both still going when killed, both oom_kill 0 — a 13h window runs 06:00->19:00 and SKIPS the
# light build every single day. Confirmed: 09-01 13:30 logged "SKIPPED: lock is held".
#
# 06:00 + 7h = 13:00, clearing 13:30 with 30 minutes of margin. Safe to truncate because this
# is an INCREMENTAL backfill: --refresh-days 7 / --target 20000 means a shorter slice deepens
# fewer games tonight and the rest are picked up tomorrow. Nothing is lost, and a daily mart
# refresh is worth more than a few hundred extra games per night.
#
# NOTE this step has never once ended on its own — every run on record is rc=137 (OOM),
# rc=143 (operator SIGTERM) or, since the 7h bound, rc=124 (its own timeout) — so its natural
# runtime is UNKNOWN and cannot be scheduled around. The bound is the point: it must yield the
# lock at a predictable time, whatever it has done.
#
# `-x` (2026-09-04): because the bound IS the schedule, ending at rc=124 is the designed
# outcome — yet cron-wrap counted it as a failure, pushed step_success{step="review_keeper"} 0
# every morning, and alert_check's check (a) breached every single day (the two real OOMs above
# were indistinguishable from that noise). With -x, rc 124/143 push success and start the job's
# success clock for check (d); rc 137 (cgroup OOM) still counts as the failure it is.
#
# `nice -n 15 ionice -c2 -n7` inside both keepers' scopes (2026-09-04), the same priority every
# nightly step gets from lib.sh's NICE: on 2 vCPUs a 16-worker drain otherwise competes with
# the two uvicorn workers as an equal. ionice is a no-op under mq-deadline/none and harmless;
# nice is what matters. Both go INSIDE systemd-run, before the python, so the scope is unchanged.
0 6 * * * /root/prospect/deploy/cron-wrap.sh -x review_keeper bash -c 'cd /root/steam-scraper && timeout 25200 systemd-run --scope --quiet -p MemoryMax=1500M -p MemorySwapMax=0 nice -n 15 ionice -c2 -n7 /root/steam-scraper/.venv/bin/python -m steam_scraper.scraper --db /root/steam-scraper/steam_games.db deepen-reviews --target 20000 --min-reviews 1 --activity-months 240 --refresh-days 7 --limit 15000 --workers 16 --rate 8.0' >> /root/deepen_backfill.log 2>&1

# ── 06:15 UTC — daytime socials keeper. OWN lock, deliberately: it must run ALONGSIDE the
# review keeper (different endpoints — store pages vs appreviews), so it must not contend for
# the refresh lock. This is the job observed leaking to 3.2GB; the MemoryMax is load-bearing.
15 6 * * * /root/prospect/deploy/cron-wrap.sh -l /root/.prospect-socials.lock socials_keeper bash -c 'cd /root/steam-scraper && timeout 46800 systemd-run --scope --quiet -p MemoryMax=1500M -p MemorySwapMax=0 nice -n 15 ionice -c2 -n7 /root/steam-scraper/.venv/bin/python -m steam_scraper.scraper --db /root/steam-scraper/steam_games.db dev-socials --min-reviews 0 --refresh-days 90 --limit 60000 --workers 8 --rate 2.0' >> /root/dev_socials_keeper.log 2>&1

# ── 13:30 UTC — midday light mart build: every mart except the two full-text monsters, which
# are copied from the published mart. Makes a data/code fix visible in ~30min instead of at
# the next nightly. Takes the refresh lock, so it skips itself if any build is running.
30 13 * * * /root/prospect/deploy/cron-wrap.sh light_build /root/prospect/deploy/light-build-cron.sh

# ── 19:15 UTC — quiet-window writers (tags_refresh, refresh_released, review_histogram),
# serial, in the 19:00-21:00 gap: all three lost the SQLite write race in the contended
# nightly lanes. quiet-window.sh enforces ONE absolute deadline across the three steps —
# the old inline `timeout 6000 bash -c 'timeout A; timeout B; timeout C'` could not, because
# each inner timeout escapes the outer's process group, so an orphaned step could keep
# holding the refresh lock past 21:00 and cost the entire nightly. The systemd scope is kept
# from the live entry so the three scrapers stay memory-capped.
15 19 * * * mkdir -p /var/log/prospect-steps && /root/prospect/deploy/cron-wrap.sh quiet1915 systemd-run --scope --quiet -p MemoryMax=1500M -p MemorySwapMax=0 /root/prospect/deploy/quiet-window.sh >> /var/log/prospect-steps/quiet1915.cron.log 2>&1

# ── 19:30 UTC — backups: NOT SCHEDULED, by operator decision (2026-08-29), reaffirmed
# 2026-09-01. deploy/backup.sh is kept and known-good (verified: sqlite3 online .backup of
# signals.db, integrity ok, 172,429 price rows matching live) — it is simply not run, and its
# alert is silenced with ALERT_CHECK_BACKUPS=0 in /root/.prospect-alerts.env.
#
# A 2026-09-01 automated project review re-enabled this line, arguing the data consequence
# outweighs the channel-noise argument. That argument is not unreasonable, but it is not the
# reviewer's call to make: the operator was asked and said no. Reverted. An agent may surface
# the tradeoff; it may not overturn an explicit human decision about someone else's data, and
# it certainly should not do so inside a 37-file commit where nobody would notice.
#
# THE CONSEQUENCE, recorded so the choice stays informed: data/signals.db is the forward-only
# follower and price series. Steam serves the CURRENT price and nothing else, so a day lost
# there is lost permanently — unlike steam_games.db, which is re-scrapeable (expensively) and
# the marts, which are rebuilt nightly from it.
#
# To turn it ON: uncomment the line below AND remove ALERT_CHECK_BACKUPS=0 from
# /root/.prospect-alerts.env. Both halves, or the staleness alert that proves the job runs
# stays blind and a silently dying backup looks exactly like the disabled state.
